# Technical Blueprint: pgvector Index Design for Originality Agent

This blueprint outlines the database schema, indexing strategy, and Python integration plan to efficiently store and query high-dimensional code vector embeddings generated by the AST parser pipeline.

---

## 1. SQL Schema Definition

Below is the PostgreSQL schema optimized for storing structural code snippets and their dense vector embeddings. It includes columns for metadata filtering, code signatures, and the `pgvector` array, along with constraints to ensure integrity.

```sql
-- Enable the pgvector extension (requires PostgreSQL 15+ and pgvector installed)
CREATE EXTENSION IF NOT EXISTS vector;

-- Table to store parsed function-level snippets and their corresponding embeddings
CREATE TABLE IF NOT EXISTS originality_embeddings (
    id SERIAL PRIMARY KEY,
    file_path TEXT NOT NULL,
    function_name VARCHAR(255) NOT NULL,
    signature TEXT,
    cleaned_source TEXT NOT NULL,
    -- Using 1536 dimensions as default (standard for OpenAI text-embedding-3-small)
    -- This should be adjusted based on the chosen encoder (e.g., 384 for MiniLM, 768 for CodeBERT)
    embedding vector(1536) NOT NULL,
    created_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP,
    
    -- Ensure uniqueness of function names within the same file to prevent duplicate indexing
    CONSTRAINT unique_file_function UNIQUE (file_path, function_name)
);

-- Metadata B-Tree Indexes for fast traditional filtering
CREATE INDEX IF NOT EXISTS idx_embeddings_file_path ON originality_embeddings (file_path);
CREATE INDEX IF NOT EXISTS idx_embeddings_func_name ON originality_embeddings (function_name);
```

## 2. Vector Indexing Strategy: IVFFlat vs. HNSW

Choosing the right indexing strategy is critical for balancing search latency, accuracy (recall), memory usage, and build speed. Below is a comprehensive comparison:

| Metric / Feature | IVFFlat (Inverted File Flat) | HNSW (Hierarchical Navigable Small World) |
| :--- | :--- | :--- |
| **Search Speed** | Fast, but scales poorly if high recall is needed. | Extremely fast (sub-millisecond queries) regardless of dimensions. |
| **Recall / Accuracy** | Moderate (~80-90%). Boundary vectors near Voronoi cells can be missed. | Very High (>98%). Graph navigation finds true nearest neighbors reliably. |
| **Memory Footprint** | Low. Only stores cluster centroids and inverted lists. | High. The entire graph structure must reside in RAM. |
| **Index Build Time** | Fast. Uses k-means clustering. | Slow. Graph build requires computing neighbors for each vector. |
| **Real-time Updates** | Bad. New vectors are placed in existing lists; needs `REINDEX` when data shifts. | Excellent. Dynamically updates graph on inserts/updates without rebuild. |
| **Prerequisites** | Requires training data (typically min. 1,000 vectors) to build index. | Can be built on empty or small tables; ready instantly. |

### Recommendation for the Originality Agent
We strongly recommend **HNSW** for the Originality Agent:
1. **Scale**: The codebase scale is small-to-medium (thousands to tens of thousands of functions). Even with 1536 dimensions, 10,000 vectors consume less than **100 MB** of memory, making HNSW's memory overhead negligible.
2. **Recall Requirements**: Plagiarism or copy-paste detection requires high search accuracy. Missing a near-duplicate code snippet because of arbitrary partitioning boundaries (which happens with IVFFlat) is unacceptable.
3. **Dynamic Updates**: Codebases are actively developed. HNSW allows instant, dynamic indexing of newly edited functions when files are saved.

### Index Creation SQL
Depending on the similarity metric, create the corresponding HNSW index:

```sql
-- Cosine Distance index (<=>)
CREATE INDEX IF NOT EXISTS idx_embeddings_hnsw_cosine 
ON originality_embeddings 
USING hnsw (embedding vector_cosine_ops)
WITH (m = 16, ef_construction = 64);

-- Inner Product index (<#>) - Optimal if embeddings are normalized to unit length
CREATE INDEX IF NOT EXISTS idx_embeddings_hnsw_ip 
ON originality_embeddings 
USING hnsw (embedding vector_ip_ops)
WITH (m = 16, ef_construction = 64);
```
> **Parameters Explained:**
> - `m = 16`: The maximum number of connection links per node in the graph. Higher increases recall but increases build time/memory.
> - `ef_construction = 64`: The size of the dynamic candidate list for constructing the graph. Larger values increase index build accuracy.

### Usage Example:
```python
from originality.db_client import DatabaseManager

# 1. Initialize schema and index configuration
# This ensures tables and HNSW indices are ready before indexing
DatabaseManager.setup_schema(vector_dim=1536)

# 2. Insert or update parsed function records
DatabaseManager.upsert_function_embedding(
    file_path="agents/originality/parser.py",
    function_name="clean_function_source",
    signature="def clean_function_source(node)",
    cleaned_source="...",
    embedding=[0.012, -0.045, ..., 0.128] # 1536 floats
)

# 3. Query similar code snippets using cosine distance
matches = DatabaseManager.query_similar_functions(
    query_embedding=[0.011, -0.043, ..., 0.130],
    limit=5,
    metric="cosine"
)

# 4. Display matching results
for idx, match in enumerate(matches, 1):
    print(f"Match #{idx}: {match['function_name']} in {match['file_path']} - Score: {match['similarity_score']:.4f}")
```
